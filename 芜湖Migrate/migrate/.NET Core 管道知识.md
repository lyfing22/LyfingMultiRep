# .NET Core 管道知识

> 面向 **Generic Host** 三大管道：配置（Configuration）、日志（Logging）、DI 容器（Dependency Injection）。
> 学完你应该能读懂任意一个 .NET Core 控制台 / Web 应用的启动代码。

---

## 第一章：Generic Host——应用的主骨架

### 1.1 为什么需要 Host？

直接写 `Console.WriteLine("Hello")` 也能跑。但一旦你需要：

- 从配置文件读参数
- 打日志
- 管理对象之间的依赖关系

自己手写管理代码很快就会变成一团乱麻。Host 就是帮你搭好这三套基础设施的**工厂**。

### 1.2 三大管道

```csharp
var builder = Host.CreateApplicationBuilder(args);
//                ↑ 这是入口，它返回一个 builder，
//                  身上挂着三个管道

// builder.Configuration   ← 配置管道
// builder.Logging         ← 日志管道
// builder.Services        ← DI 容器

var host = builder.Build();
//        ↑ Build() 之后三个管道全部冻住，不能再加东西
//        返回 IHost，通过 host.Services 拉取服务
```

| 管道 | 类比 | 职责 |
|------|------|------|
| **配置** | 一个多层的备忘录 | 从文件/环境变量/命令行收集键值对，按优先级覆盖 |
| **日志** | 一个广播站 | 你喊一声（`logger.LogInformation`），多个输出端同时收到 |
| **DI 容器** | 一个智能工具箱 | 你告诉它你需要什么零件，它自动帮你拼好 |

### 1.3 完整代码示例

```csharp
using Microsoft.Extensions.Hosting;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Logging;

var builder = Host.CreateApplicationBuilder(args);

// === 配置管道 ===
// 默认已加载 appsettings.json + 环境变量 + 命令行参数

// === 日志管道 ===
builder.Logging.ClearProviders();
builder.Logging.AddConsole();  // 输出到控制台

// === DI 容器 ===
builder.Services.AddSingleton<MyService>();

var host = builder.Build();  // ← 冻住，之后不能再改

// === 运行时 ===
var logger = host.Services.GetRequiredService<ILogger<Program>>();
logger.LogInformation("Hello from Generic Host");

var svc = host.Services.GetRequiredService<MyService>();
svc.DoSomething();

public class MyService { public void DoSomething() { } }
```

### 1.4 口诀

```
Configure（搭管道：加配置源、注册服务、配日志）
  → Build（冻住：验证依赖关系，生成 ServiceProvider）
    → Run（通水：拉服务干活）
```

### 1.5 延伸：WebApplication vs Host

```csharp
// 控制台应用
var builder = Host.CreateApplicationBuilder(args);

// Web 应用（ASP.NET Core）
var builder = WebApplication.CreateBuilder(args);
```

`WebApplication.CreateBuilder` 继承自 `Host.CreateApplicationBuilder`，额外多了：

- 路由系统（`app.MapGet`、`app.MapPost`）
- 中间件管道（`app.UseAuthentication()`）
- Kestrel 服务器（监听 HTTP 请求）

Web 应用的内部结构：

```
WebApplication.CreateBuilder
  └─ Host.CreateApplicationBuilder  ← 仍然有配置/日志/DI
  └─ 注册 Kestrel 服务器
  └─ 注册中间件管道

WebApplication app = builder.Build();
//  ↑ 既是 IHost，又有 MapGet/Use/Run 等 Web 方法
```

## 第二章：配置管道——数据从哪来到哪去

### 2.1 配置源栈

`builder.Configuration` 维护一个**配置源列表**（`IConfigurationSource` 的集合），后注册的覆盖前注册的。

```csharp
// 默认注册顺序（无需手动加）
builder.Configuration
    .AddJsonFile("appsettings.json", optional: false)           // 基础配置
    .AddJsonFile("appsettings.Development.json", optional: true) // 环境覆盖
    .AddEnvironmentVariables()                                    // 服务器级别覆盖
    .AddCommandLine(args);                                        // 最高优先级
```

**查值规则**：从后往前查，找到第一个即返回。

**例子**：

```json
// appsettings.json
{ "Timeout": 30, "Mode": "batch" }
```

```bash
# 环境变量
set Timeout=60

# 命令行
--Mode=debug
```

**最终结果**：`Timeout = 60`（来自环境变量），`Mode = "debug"`（来自命令行）。

### 2.2 AddJsonFile vs AddJsonStream

为什么我们的项目用了 `AddJsonStream` 而不是 `AddJsonFile`？

```csharp
// 写法 A（框架自带的，95% 的项目用这个）
builder.Configuration.AddJsonFile("appsettings.json");

// 写法 B（我们的写法——为了支持 // 注释）
var raw = File.ReadAllText("appsettings.json");
var clean = StripJsonLineComments(raw);  // 手动剥掉 // 注释
builder.Configuration.AddJsonStream(new MemoryStream(Encoding.UTF8.GetBytes(clean)));
```

**核心问题**：`System.Text.Json` 的 `JsonDocument.Parse()` **默认不允许 // 注释**。

```
AddJsonFile("appsettings.json")
  → 框架内部从文件读取文本
  → 交给 JsonDocument.Parse()
  → JsonCommentHandling.Disallow（硬编码）
  → appsettings.json 里有 // 注释 → 抛出 JsonException ❌
```

```
AddJsonStream(new MemoryStream(...))
  → 我们先读文件 → 剥注释 → 再以流的方式喂给框架
  → JsonDocument.Parse() 收到的已经是干净 JSON
  → 正常运行 ✅
```

**完整对比表**：

| 对比项 | `AddJsonFile` | `AddJsonStream` |
|--------|---------------|-----------------|
| 谁读文件 | 框架内部读取 | 你手动读完再传 |
| 支持 `//` 注释 | ❌ 直接抛异常 | ✅ 你先剥干净再传 |
| 支持热重载 | ✅ `reloadOnChange: true` | ❌ 一次性加载 |
| 文件路径 | 填相对路径即可 | 不关心路径，你给流就行 |

> **一句话**：`AddJsonStream` 本身也不允许注释——但我们把注释剥离放在管道之外自己处理，所以绕过了这个限制。

### 2.3 强类型绑定（关键环节）

从 JSON 字符串到 C# 对象，中间经过两步：

```
appsettings.json（磁盘上的文本）
  → IConfiguration（键-值字典，树形结构）
    → MigrationOptions（强类型 C# 对象）
```

第二步就是 `config.Bind(options)`：

```csharp
// ========== 这段代码要完整看 ==========

// 1. 创建一个空的对象，所有属性的值都是默认值
var options = new MigrationOptions();

// 2. 把 IConfiguration 中的数据按名称匹配到这个对象
//    内部使用反射：遍历 options 的每个属性 → 在 config 中找同名 key → 赋值
config.Bind(options);

// 3. 现在 options 已经被填满了，可以直接用
var mode = options.Migration.Mode;       // "batch"
var timeout = options.Upload.TimeoutSeconds;  // 30
var connStr = options.ConnectionStrings.Source;  // "User Id=..."
```

**MigrationOptions 的完整定义**（让你一眼看清所有配置项）：

```csharp
public class MigrationOptions
{
    public string SourceType { get; init; } = "Oracle";
    public ConnectionStringsOption ConnectionStrings { get; init; } = new();
    public MigrationConfig Migration { get; init; } = new();
    public UploadConfig Upload { get; init; } = new();
    public IdentityConfig Identity { get; init; } = new();
    public Dictionary<string, DeviceDptInfo> ModalityDepartment { get; init; } = new();
}

public class ConnectionStringsOption
{
    public string Source { get; init; } = "";
    public string Destination { get; init; } = "";
    public string MongoDB { get; init; } = "";
}

public class MigrationConfig
{
    public string Mode { get; init; } = "batch";
    public int PageSize { get; init; } = 100;
    public int Parallelism { get; init; } = 4;
    // ... 其他属性
}
```

**JSON ↔ C# 对照表**（Bind 的匹配规则）：

```
JSON 键路径                              C# 属性路径                             结果示例
────────────────────────────────────────────────────────────────────────────────────────
"SourceType"                            options.SourceType                       "Oracle"
"ConnectionStrings:Source"              options.ConnectionStrings.Source         "User Id=..."
"ConnectionStrings:Destination"         options.ConnectionStrings.Destination    "server=..."
"ConnectionStrings:MongoDB"             options.ConnectionStrings.MongoDB        "mongodb://..."
"Migration:Mode"                        options.Migration.Mode                   "batch"
"Migration:PageSize"                    options.Migration.PageSize               100
"Migration:Parallelism"                 options.Migration.Parallelism            4
"Upload:Url"                            options.Upload.Url                       "http://..."
"Upload:TimeoutSeconds"                 options.Upload.TimeoutSeconds            30
"Identity:StorageNode"                  options.Identity.StorageNode             "HINAMIISFBS"
"Identity:HospitalName"                 options.Identity.HospitalName            "空总医院"
```

**匹配规则的规律**：

- 冒号 `:` 是 JSON 路径分隔符，对应 C# 对象树的层级
- 属性名大小写不敏感（内部用 `StringComparer.OrdinalIgnoreCase`）
- JSON 中有但 C# 中找不到的属性 → 静默忽略，不报错
- C# 中有但 JSON 中找不到的属性 → 保持默认值（`default` 或属性初始值）

### 2.4 延伸：Options 模式

除了手动 `Bind`，.NET Core 还提供了完整的 `IOptions<T>` 体系：

```csharp
// 方式 A：手动 Bind（我们的用法）
var options = new MigrationOptions();
config.Bind(options);

// 方式 B：IOptions<T> 注入（标准做法）
services.Configure<MigrationOptions>(config.GetSection("Migration"));

public class SomeService
{
    public SomeService(IOptions<MigrationOptions> options)
    {
        var mode = options.Value.Mode;  // 通过 .Value 访问
    }
}
```

三种 Options 接口：

| 接口 | 生命周期 | 能否热更新 | 适用场景 |
|------|---------|-----------|---------|
| `IOptions<T>` | Singleton | ❌ 快照固定 | 启动后不变化的配置 |
| `IOptionsSnapshot<T>` | Scoped | ✅ 每次请求重新读 | Web 应用中需要最新值 |
| `IOptionsMonitor<T>` | Singleton | ✅ 注册回调通知 | 需要监听配置变化 |

## 第三章：日志管道——ILogger\<T\> 的工作原理

### 3.1 核心概念

```csharp
// 你只需要注入这个接口
public class MyService
{
    private readonly ILogger<MyService> _logger;
    public MyService(ILogger<MyService> logger)
    {
        _logger = logger;
    }

    public void DoWork()
    {
        _logger.LogInformation("工作中...");
    }
}
```

**问题**：`ILogger<T>` 到底写到了哪里？

### 3.2 日志流的全链路

```
业务代码                        框架层                    实现层
ILogger<T>.LogInformation()
  → ILoggerProvider[] 遍历
    → ConsoleLoggerProvider     → Console.WriteLine()
    → SerilogLoggerProvider    → Serilog Pipeline
                                  → Console Sink
                                  → File Sink
```

### 3.3 为什么 ILogger\<T\> 带泛型 T？

`T` 是**分类器**，不是"记录 T 类型数据"。

```csharp
var log1 = sp.GetRequiredService<ILogger<Program>>();
var log2 = sp.GetRequiredService<ILogger<MigrationEngine>>();

// log1 和 log2 是两个不同的实例，可以独立控制日志级别
```

**配置不同级别**（appsettings.json）：

```json
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",            // 默认：Information 及以上
      "DataMigrate.Core.MigrationEngine": "Warning"  // MigrationEngine 只打 Warning+
    }
  }
}
```

`ILogger<Program>` 的分类名就是 `"DataMigrate.Program"`，`ILogger<MigrationEngine>` 的分类名是 `"DataMigrate.Core.MigrationEngine"`。

### 3.4 替换日志提供程序

```csharp
builder.Logging.ClearProviders();   // 移除默认的 4 个提供程序
builder.Logging.AddSerilog();       // 只保留 Serilog
```

**为什么 ClearProviders？** 默认注册了 Console/Debug/EventSource/EventLog 四个提供程序。不清掉的话，每个 `logger.LogInformation` 会同时输出到控制台 + 调试窗口 + 事件日志 + Serilog 文件——日志会重复四份。

### 3.5 延伸：结构化日志

传统日志是字符串拼接：

```csharp
_logger.LogInformation($"用户 {userId} 登录成功");
```

结构化日志是**命名占位符**：

```csharp
_logger.LogInformation("用户 {UserId} 登录成功", userId);
```

区别在于：后者不仅输出可读文本，还会把 `UserId` 作为字段存储。查询系统可以按 `UserId` 过滤所有相关日志，不需要全文搜索。

## 第四章：DI 容器——服务注册与解析

### 4.1 三种注册方式与各自场景

```csharp
// ─── 方式 1：类型注册（DI 自动构造实例）───
builder.Services.AddSingleton<MigrationStatistics>();
// 等价于：容器在第一次需要时自动 new MigrationStatistics()
// 条件：MigrationStatistics 的构造函数参数必须全部来自 DI 容器

// ─── 方式 2：实例注册（手动构造，容器只负责持有）───
builder.Services.AddSingleton(new JwtTokenManager(appId, node, expiry, secret));
// 等价于：你自己 new 好了，交给容器保管
// 适用：构造参数来自配置，不是来自 DI 容器

// ─── 方式 3：工厂注册（延迟构造，需要其他 DI 服务）───
builder.Services.AddSingleton(sp => new PostMigrationAuditor(
    connStr,
    sp.GetRequiredService<ILogger<PostMigrationAuditor>>()));
// 等价于：等到第一次有人要 PostMigrationAuditor 时才执行这个函数
// 适用：构造时需要从 sp 拿别的服务
```

**选型决策树**：

```
构造函数有没有参数？
  ├─ 无参 → 方式 1（AddSingleton<T>）
  └─ 有参
       ├─ 参数来自配置值 → 方式 2（new T(...)）
       └─ 参数需要从 DI 拿 → 方式 3（sp => new T(...)）
```

### 4.2 三种生命周期

| 生命周期 | 创建时机 | 实例数量 | 适用场景 |
|----------|---------|---------|----------|
| `Singleton` | 首次被请求时（或 Build 时） | 整个进程 1 个 | 无状态服务、共享状态 |
| `Scoped` | 每个作用域创建时 | 每个作用域 1 个 | Web 请求（每个请求一个 DbContext）|
| `Transient` | 每次被请求时 | 每次都新建 | 轻量无状态服务 |

```csharp
services.AddSingleton<IService, MyService>();  // 全局唯一
services.AddScoped<IService, MyService>();     // 每个作用域一个
services.AddTransient<IService, MyService>();  // 每次都 new
```

**本项目为什么全部用 Singleton？** 因为这是控制台应用，没有"请求"概念，整个运行期就是一个大作用域。Singleton 和 Transient 在这里表现一样。

### 4.3 Keyed DI——运行时多选一

**问题**：一个接口有多个实现，运行时根据配置选择用哪个。

**错误做法**：

```csharp
// 注册两个实现
services.AddSingleton<IMigrationSource, OracleSource>();
services.AddSingleton<IMigrationSource, SqlServerSource>();

// 使用时——到底返回哪个？
var source = sp.GetRequiredService<IMigrationSource>();
// ↑ 返回最后注册的那个！完全取决于注册顺序，不可靠
```

**正确做法（Keyed DI，.NET 8 引入）**：

```csharp
// 注册时给每个实现带一把"钥匙"
services.AddKeyedSingleton<IMigrationSource, OracleSource>("Oracle");
services.AddKeyedSingleton<IMigrationSource, SqlServerSource>("SqlServer");

// 使用时按钥匙取
var key = config["SourceType"];  // 从配置读：可能是 "Oracle"
var source = sp.GetRequiredKeyedService<IMigrationSource>(key);
// key = "Oracle"   → 返回 OracleSource
// key = "SqlServer" → 返回 SqlServerSource
```

**内部原理**：

```
注册时：
  DI 容器内部维护一个映射表：
  (IMigrationSource, "Oracle")       → OracleSource 的工厂函数
  (IMigrationSource, "SqlServer")    → SqlServerSource 的工厂函数

解析时：
  GetRequiredKeyedService<IMigrationSource>("Oracle")
  → 查表 → 找到 (IMigrationSource, "Oracle")
  → 调用工厂函数 → 返回 OracleSource 实例
```

**为什么不用 switch？**

```csharp
// 不用 Keyed DI 的话，你得写：
IMigrationSource source = options.SourceType switch
{
    "Oracle" => sp.GetRequiredService<OracleSource>(),
    "SqlServer" => sp.GetRequiredService<SqlServerSource>(),
    _ => throw new NotSupportedException()
};
// 每次加新数据源，都要改这里的 switch
```

Keyed DI 把选择逻辑从代码移到了配置，新增一个数据源只需要：

```
1. 写一个新的实现类
2. 加一行 AddKeyedSingleton
3. 改 appsettings.json 里的 SourceType
```

调度代码一行不动——**开放封闭原则**。

### 4.4 延伸：TryAdd / 防止重复注册

```csharp
// 如果已经有 IMyService 的注册，Add 会直接跳过，不会报错
services.TryAddSingleton<IMyService, MyService>();

// 对比：Add 会覆盖之前的注册
services.AddSingleton<IMyService, MyServiceA>();
services.AddSingleton<IMyService, MyServiceB>();  // 覆盖了 A
```

`TryAdd` 在库/模块的代码中很常用——你不知道用户是否已经在前面注册了自己的实现，如果已经注册了就保留用户的，否则用默认的。

## 第五章：HttpClientFactory——为什么不该 new HttpClient()

### 5.1 new HttpClient() 有什么问题？

```csharp
// ❌ 错误写法
for (int i = 0; i < 100; i++)
{
    using var client = new HttpClient();
    await client.PostAsync(url, content);
}
```

**后果**——端口耗尽：

```
每次 new HttpClient()
  → 创建一个新的 SocketsHttpHandler（底层网络处理器）
  → 发起请求时占用一个本地 TCP 端口
  → Dispose() 不会立即释放端口
  → 端口进入 TIME_WAIT 状态（约 240 秒）
  → 高并发下快速耗尽所有可用端口（默认范围约 16,384 个）
  → 抛出 SocketException: 地址已在使用中
```

**示意图**：

```
时间 → 
请求 1: 建立连接 → 传输 → 关闭 → TIME_WAIT (240s)
请求 2: 建立连接 → 传输 → 关闭 → TIME_WAIT (240s)
请求 3: 建立连接 → 传输 → 关闭 → TIME_WAIT (240s)
...
请求 16384: 端口耗尽 ❌
```

### 5.2 AddHttpClient\<T\> 的解决方案

```csharp
builder.Services.AddHttpClient<ArchiveUploader>(client =>
{
    client.BaseAddress = new Uri("http://api.example.com");
    client.Timeout = TimeSpan.FromSeconds(30);
    client.DefaultRequestHeaders.Add("Accept", "application/json");
}).ConfigurePrimaryHttpMessageHandler(() => new HttpClientHandler
{
    MaxConnectionsPerServer = 16  // 连接池中每个服务器的最大连接数
});
```

**内部原理**：

```
AddHttpClient<ArchiveUploader>
  └─ 注册 IHttpClientFactory（Singleton）
  └─ 注册 ArchiveUploader（Transient，构造函数注入 HttpClient）

第一次 GetService<ArchiveUploader>()
  └─ IHttpClientFactory 创建或从池中取 SocketsHttpHandler
  └─ 用这个 Handler 创建 HttpClient
  └─ 应用配置（BaseAddress, Timeout, Headers）
  └─ 注入到 ArchiveUploader 的构造函数

第二次 GetService<ArchiveUploader>()
  └─ 从池中复用同一个 SocketsHttpHandler（连接复用！）
  └─ 创建一个新的 HttpClient 实例（轻量，配置相同）
```

**连接池的核心**：`SocketsHttpHandler` 是重的（负责 TCP 连接管理），`HttpClient` 是轻的（只是配置包装）。`IHttpClientFactory` 池化管理 `SocketsHttpHandler`，每个请求只 new 轻量的 `HttpClient`。

### 5.3 Typed Client vs Named Client

```csharp
// ─── Typed Client（推荐，强类型）───
builder.Services.AddHttpClient<ArchiveUploader>(client => { ... });
// ArchiveUploader 的构造函数注入 HttpClient
// 使用方只需要注入 ArchiveUploader，不知道 HttpClient 的存在
public class ArchiveUploader
{
    public ArchiveUploader(HttpClient http) { ... }
}

// ─── Named Client（灵活，运行时选名字）───
builder.Services.AddHttpClient("PACS", client => { ... });
// 使用时按名字取
var factory = sp.GetRequiredService<IHttpClientFactory>();
var client = factory.CreateClient("PACS");
```

### 5.4 MaxConnectionsPerServer 调优

```csharp
.ConfigurePrimaryHttpMessageHandler(() => new HttpClientHandler
{
    MaxConnectionsPerServer = options.Migration.Parallelism * 4
});
```

为什么是 `Parallelism × 4`？

```
4 个消费者并行上传
每个消费者同一时刻可能有多个在途请求
  （一个请求在等 HTTP 响应时，下个请求已发出）
× 4 预留余量
= 16 个并发连接足够，不会串连等待
```

默认值在不同环境不同（.NET Core 3.1+ 是 `int.MaxValue`），但某些代理/防火墙有限制。主动设一个合理的值更可控。

## 第六章：Keyed DI 深入（回答你的提问）

### 6.1 完整的注册解析

```csharp
builder.Services.AddKeyedSingleton<IMigrationSource, OracleSource>("Oracle");
```

这句话拆解：

| 部分 | 含义 |
|------|------|
| `AddKeyedSingleton` | 生命周期 = Singleton，且这是一个**带 Key** 的注册 |
| `<IMigrationSource>` | 服务类型（接口或抽象类），即你请求时用的类型 |
| `<OracleSource>` | 实现类型，即容器实际创建的具体类 |
| `("Oracle")` | 钥匙（Key），一个 `object`，通常是字符串 |

**注册后的内部状态**（伪代码）：

```csharp
// DI 容器内部多了这么一条记录
new ServiceDescriptor(
    serviceType: typeof(IMigrationSource),
    implementationType: typeof(OracleSource),
    lifetime: ServiceLifetime.Singleton,
    serviceKey: "Oracle"  // ← 这一列是 Keyed DI 新增的
);
```

### 6.2 解析时发生了什么

```csharp
var source = sp.GetRequiredKeyedService<IMigrationSource>(options.SourceType);
// options.SourceType = "Oracle"（来自 appsettings.json）
```

步骤：

```
1. 容器收到请求：找 IMigrationSource 的 "Oracle" 注册
2. 查内部映射表：(IMigrationSource, "Oracle") → OracleSource 的工厂
3. 如果是首次：创建 OracleSource 实例，存入 Singleton 缓存
4. 返回实例
```

### 6.3 为什么不用普通的 AddSingleton

```csharp
// 方案 A：普通 Singleton
services.AddSingleton<IMigrationSource, OracleSource>();
services.AddSingleton<IMigrationSource, SqlServerSource>();  // 再加一个

var a = sp.GetRequiredService<IMigrationSource>();   // ← 返回 SqlServerSource（最后注册的）
var b = sp.GetServices<IMigrationSource>();           // ← 返回两个，但你自己得区分

// 方案 B：Keyed DI
services.AddKeyedSingleton<IMigrationSource, OracleSource>("Oracle");
services.AddKeyedSingleton<IMigrationSource, SqlServerSource>("SqlServer");

var a = sp.GetRequiredKeyedService<IMigrationSource>("Oracle");    // ← 明确要 Oracle
var b = sp.GetRequiredKeyedService<IMigrationSource>("SqlServer"); // ← 明确要 SqlServer
```

| 场景 | 普通 `AddSingleton` | `AddKeyedSingleton` |
|------|-------------------|---------------------|
| 一个接口只有一个实现 | ✅ 简洁好用 | 没必要，有点过度设计 |
| 一个接口有 N 个实现，运行时选择 | ❌ `GetService` 返回最后注册的 | ✅ 按 key 精确选择 |
| 新增一个实现需要改哪些代码 | 类 + 注册 + 调用方的选择逻辑 | 类 + 一行注册（调用方不改） |

### 6.4 Key 的类型

Key 可以是任意 `object` 类型，字符串最常用，因为可以直接对应 JSON 配置：

```csharp
// 字符串 key（最常用）
services.AddKeyedSingleton<IMyService, ImplA>("A");
services.AddKeyedSingleton<IMyService, ImplB>("B");

// 枚举 key（编译期类型安全）
services.AddKeyedSingleton<IMyService, ImplA>(DataSourceType.Oracle);
services.AddKeyedSingleton<IMyService, ImplB>(DataSourceType.SqlServer);

// 整数 key
services.AddKeyedSingleton<IMyService, ImplA>(1);
services.AddKeyedSingleton<IMyService, ImplB>(2);
```

## 附录：常见问题速查

**Q：`config.Bind(options)` 找不到属性会怎样？**
A：静默忽略，不报错。JSON 有多余键不影响，C# 找不到的属性保持默认值。

**Q：`AddJsonFile` 的参数 `optional: true` 是什么含义？**
A：文件不存在时是否报错。`true` = 跳过，`false` = 抛 `FileNotFoundException`。

**Q：Singleton 服务会被释放吗？**
A：如果实现了 `IDisposable`，Host 关闭时自动调用 `Dispose()`。

**Q：`Build()` 之后还能加服务吗？**
A：不能。`IServiceCollection` 在 `Build()` 之后冻结，再调用 `AddSingleton` 会抛出异常。

**Q：什么时候用 Typed Client，什么时候用 Named Client？**
A：Typed Client 更常用——强类型、构造函数注入、单元测试友好。Named Client 适用于同一个 `HttpClient` 配置需要在多处使用且通过名字区分的情况。
